## 1. 制作の前提と最初の検証

**本作のキャラクターモチーフはウミウシ。** 以前の「モップうさぎ」「重いくま」は技術的な概念実証（PoC）の仮モデルであり、**本番のデザイン・制作対象ではない**。外観や道具の設定を引き継がない。

一方で、**ウミウシがモチーフだからといって、水中や海底を舞台にするわけではない。** ステージはメダルを押し合い、敵が橋から侵入し、奈落へ落ちる「不思議な卓上遊戯装置」として独立に設計する。海洋生物の形態から美術言語を借りることと、世界全体を海にすることは別問題。

最初に作るのは、**ノーマルメダル、ウミウシ型Pusherのシルエット試作、ステージ床の造形試作**の3D素材と、**Copernicus製のメダル図鑑アイコン、UIパネル見本**の2D素材。ウミウシ型Pusherは最終キャラクターではなく、共通設計を検証するための第一候補とする。

| 順番 | 制作物 | この段階で確かめたいこと |
|---|---|---|
| 0 | ウミウシの形態リファレンス、Pusherのシルエット3案、ステージ意匠2案、配色テスト | 海中表現なしでもNudraらしいか。見下ろしで役割が読めるか |
| 1 | ノーマルメダル、Pusher試作1体、床、図鑑アイコン1点、UIパネル1点 | 3D/2Dの統一感、寸法、物理形状、視認性 |
| 2 | 橋、出現足場、ゴール、カタパルト、通常敵の試作 | ステージ01が遊戯装置として一式成立するか |
| 3 | Pusherのバリエーション、中ボス、最終ボス、素材メダル16種 | キャラクターの役割差・戦闘力の表現 |
| 4 | 錬成メダル72種と図鑑画像、レール、メニューUI素材 | 一貫した生成ルールで量産できるか |
| 5 | 短い動作、エフェクト用素材 | Bevyでの動作・演出接続を確認 |

名前・キャラクター数・各個体の見た目は未確定。旧PoCの名称や外観を正式仕様として固定しない。メダル89種のID・名称は既存カタログを正本とする。

## 2. アートディレクション

### 2.1 主役は「ウミウシらしいキャラクター」であって「海底ステージ」ではない

ウミウシの魅力は、水辺という背景なしでも成立する**小さな体の大胆な輪郭・奇妙な突起・色柄・ゆっくりした動き**にある。参考にする特徴は次のとおり。

- **触角（嗅角／rhinophores）**：頭側の2本の突起。正面・上面からの識別点。短いタイプ、太いタイプ、葉状タイプなどの変化をつける。
- **外套膜（mantle）と縁のひらひら**：体の輪郭や動きの柔らかさ。薄すぎて画面で消える構造にはしない。
- **背面の鰓・突起（cerataなど）**：背中側に特徴を集中できる。ただし実際のウミウシの種類によって構造は異なるため、全キャラへ全部盛りにしない。
- **大胆な警戒色・斑点・縁取り**：小さい表示でも認識できる2〜3色の色面へ整理する。現実の種を忠実に復元する必要はない。
- **ぬめりではなく、ぷにっとした弾力**：おもちゃのような柔らかい質感。過剰な透明感や濡れ表現で視認性を損なわない。

**避ける短絡**：サンゴ、海藻、貝殻、泡、水流、青い水中光、砂浜、潜水具を背景や装置へ自動採用しない。「ウミウシ＝海」を装飾の言い訳にしない。水属性メダルや水系演出はもちろん使ってよいが、作品全体の環境設定にはしない。

### 2.2 戦闘ゲームとしてのシルエット

**メダルを撃ち込み、Pusherが押し、敵が奈落へ落ちる、気軽でコミカルなバトル。** かわいさだけでなく、行動と戦闘性能が想像できることを重視する。

- 味方Pusherは低い重心、押す面の幅、踏ん張りやすさを見せる。**必ずしも道具を手に持たせない**。体の前縁・硬い外套膜・着脱できる押し板なども候補。
- 敵は同じウミウシモチーフを使ってもよいが、通常敵・中ボス・最終ボスで**輪郭、突起のリズム、色面、歩幅**を明確に変える。敵の種族・設定は未確定とする。
- ボスは巨大化だけではなく、突起の冠、広がった外套膜、明確な装甲など、ひと目で強そうな造形を検討する。
- 画面の上から見て、メダル・味方・敵・設備が背景に埋もれない配色にする。

錬成メダルは「サウナ」「激辛」「願い」「チェーンソー」など、少し意外でも**戦闘力・特殊効果が想像できる**図案にする。かわいくするためだけに弱そうな日用品へ置き換えない。

### 2.3 ステージは独立した「遊戯装置」

最初のステージは、架空の展示台・実験装置・からくり盤のような**人工的なメダルバトルの舞台**とする。主役のウミウシ造形と対比する、硬質な床・規則的なレール・明瞭な段差を基本にする。

| 意匠候補 | 方向性 | 注意点 |
|---|---|---|
| 不思議な遊戯盤 | 面取りした台、視認性の高いライン、差し色、ゲーム機的な仕掛け | コインが埋もれる過密模様にしない |
| 小さなからくり劇場 | 橋・入口・ゴールに舞台装置らしい意味づけ | 舞台の飾りが移動経路を隠さない |
| おもちゃの実験場 | 幾何学的な床、仕切り、交換式の装置パーツ | 無機質すぎてキャラクターと分離しない |

**これらは方向性の比較案であり、舞台設定の決定ではない。** 初回の2案は「同じゲーム形状を別の美術言語で着せ替える」検証とし、マップ構造や難易度を勝手に変更しない。奈落は床の外側や下方への落下空間であり、水面で表現しない。

### 2.4 HoudiniとCopernicusで統一する表現

キャラクターの外套膜の縁、突起の反復、斑点・縞模様、舞台装置の面取り・ラインはHoudiniのプロシージャルパラメータにする。Copernicusで生成した配色・模様・マスクを**3Dのテクスチャ、キャラクター選択サムネ、メダル図鑑、UI装飾**へ展開する。ただしステージUIまで海洋モチーフで統一する必要はない。

## 3. 画面での見え方と共通ルール

### 3.1 見下ろしで読みやすい形

現在は3Dの盤面を、手前上空から約60度で見下ろす固定カメラ。画面上が敵の入口、画面下がカタパルトとゴールになる。

メダルの上面、触角、外套膜の輪郭、背面突起、押す面など、**上から見える部分**に特徴を置く。

正面の顔だけ、側面の細かな模様だけに頼らない。小さく表示しても、味方・通常敵・大きな敵を見分けられることを優先する。

制作中は次のカメラを確認用に使える。カメラとライトは確認用シーンに置き、モデルのGLBへの書き出し対象から外す。

| 項目 | 現在の値 |
|---|---|
| カメラ位置 | `(0, 25, 14)` |
| 注視点 | `(0, 0, -0.8)` |
| 画角 | 縦FOV 32度、透視投影 |

### 3.2 座標・寸法・原点

- ゲーム座標は右手系、**Yが上、Xが左右、Zが奥行き**。
- 1単位をゲーム上の1mとして扱う。これはプロトタイプのゲームスケールであり、現実の硬貨の実寸には縮小しない。
- 以下の寸法は現在の定義・物理形状に合わせる基準値。最終的な物理バランスはゲーム側で調整する。
- 書き出しの最上位ノードは `root_game` とし、移動・回転を0、スケールを1に揃える。
- Houdiniの作業用原点は自由。納品GLBでは次の表に合わせ、必要なら書き出し用の親ノード・ジオメトリ移動で補正する。

| 種類 | 納品GLBの原点・向き |
|---|---|
| メダル | 円盤の中心。厚み方向はY。上面は+Y |
| Pusher | 物理ボックスの中心。従来の高さ0.8なら足元はローカルY=-0.4。進行方向の基準は+X、押す面の幅はZ方向。形状・寸法は新キャラ採用時に確定 |
| 敵 | カプセルの中心。足元はローカルY=-高さ/2。初期の正面は+Z（現在の橋から盤面へ歩く向き） |
| 床・橋・出現足場 | 厚みを含む中央。厚さ0.5なら上面はローカルY=+0.25 |
| カタパルト | 接地面の中央。射出方向は-Z |
| ゴール、追加のレール部品 | 接地面の中央。ゴールの見た目は接地点へ配置し、判定中心の高さだけゲーム側で補正する |

原点は見た目を接続するための約束で、Houdiniで物理シミュレーションを焼き込むためのものではない。

メダルの転がり・積み重なり・落下と、キャラクターの移動位置はゲーム側の物理演算が担当する。

## 4. 制作物の一覧

### 4.1 メダル

共通の円盤をマスターとして制作し、上下面の絵柄、浅いレリーフ、縁、材質で種類を作り分ける。

**89種それぞれを一から別の立体物としてモデリングする依頼ではない。**

| 項目 | 希望する内容 |
|---|---|
| 基本形 | 平たい円盤。小さな面取り、上下面、横から見ても分かる縁 |
| 通常サイズ | 半径0.28、直径0.56、厚さ0.08 |
| 太陽 `sun` | 現在の定義では半径0.42、直径0.84、厚さ0.08。大きい円盤の派生形 |
| 原点 | 円盤中心。通常サイズのY範囲は-0.04〜+0.04 |
| ノーマル | 金色系を出発点とする。縁と中央の模様だけでも識別できる形 |
| 素材16種 | 共通の縁＋大きな属性記号。色と形の両方で区別する |
| 錬成72種 | 錬成名を表す大きな記号・イラスト・浅いレリーフ |
| 裏面 | 裏返っても種類を識別できる絵柄。同じ図案の両面使用でよい |
| レベル差 | 初回はLv.1〜4で同じモデルを使用する。現在は全レベルで寸法が同じ。356個のモデルは不要 |

メダルの**描画GLBとコライダーは別管理**とする。初回はゲーム側の円柱などの単純形状を利用し、Houdini製の当たり判定メッシュを必須にはしない。

絵柄が輪郭から大きく飛び出すと、円柱の衝突形状と見た目がずれる。

唐辛子やチェーンソーなども、まずは円盤上の図柄として収める。高い浮き彫りより、上から読める大きな面を優先する。

素材の図案案:

| 素材 | 図案案 | 素材 | 図案案 |
|---|---|---|---|
| 炎 | ふっくらした炎 | 砂 | 砂山と粒 |
| 水 | 大きなしずく | 光 | 光のきらめき |
| 浄化 | きれいになる泡・清めの印 | 血 | 赤いしずく |
| 毒 | きのこ・毒びん | 雷 | 太い稲妻 |
| 風 | 渦を巻く風 | 幻 | きつね・ゆらぐ影 |
| 死 | かわいいおばけ | 星 | 五角星 |
| 時 | 時計 | 刃 | 短い刃 |
| 太陽 | 丸い太陽 | 山 | 山の稜線 |

図案と配色は提案であり、名前とIDを保ったまま制作しやすい表現に調整してよい。

メダルの全IDと表示名は末尾の一覧、組み合わせの正本は[錬成表](medal-fusions.csv)を参照する。

### 4.2 味方Pusher（ウミウシモチーフで再設計）

**旧PoCの `mop_rabbit` / `iron_bear` は正式制作対象から除外する。** 現在のゲーム実装に残っているIDや物理ボックス値は、移行までの技術的な仮仕様であり、キャラクター設定ではない。

まずは**同じウミウシ系統から複数のプレイスタイルが読み取れる**シルエット案を作る。キャラ名・最終的な個体数・能力値は別途決める。

| 概念案 | 造形の方向性 | 伝わる印象 | ゲーム上の検証 |
|---|---|---|---|
| 標準タイプ | 低く丸い胴体、短い触角、幅広の前縁 | 押す力が素直に伝わる | メダルに接する前面の位置と幅 |
| すばやいタイプ | 細長い輪郭、流れる外套膜、小ぶりな背面突起 | 軽快・小回り | 同じ床上での視認性、装飾のはみ出し |
| 重量タイプ | 幅のある外套膜、まとまった突起、大きな接地シルエット | ずっしり・強い押し | 物理形状と見た目の乖離を抑える |

上の3案は**デザイン比較用の仮説**であり、3キャラの登場や性能を確定するものではない。貝殻を背負わせる必要も、モップ・ローラーを持たせる必要もない。

- 前方はローカル`+X`、押す有効幅は`Z`方向。これらは当面、既存Pusherのゲーム接続に合わせる。
- **胴体・外套膜・触角・背面突起・押す部位**を必要に応じて名前付き部品にし、色柄差し替えやアニメーションを可能にする。
- 触角や薄いヒラヒラは見た目用であり、物理ボックスをむやみに拡張しない。
- 最初は押す姿勢の静止モデルでよい。軟体のたわみや突起の揺れは、Bevyの移動と分離したローカルアニメーション候補とする。
- レールに沿って往復する現在の動作仕様を尊重し、往復のたびにモデルが自動で反転するとは仮定しない。

### 4.3 敵（ウミウシと対比する戦闘キャスト）

敵もウミウシの形態を応用する案を第一候補とするが、**全員を同じウミウシ種に固定しない**。主役とシルエットが重複する場合は、外套膜や突起の種類・形・配色を変える。種族のストーリー設定はここでは決めない。

| 実装上の仮ID | 役割 | 現行コライダーの外形（直径×高さ） | ビジュアル検証案 |
|---|---|---|---|
| `grunt` | 多数出る通常敵 | `0.6 × 0.9` | 小さく単純な輪郭、短い突起。群れでも見失わない |
| `brute` | 第1〜3Waveの中ボス | `1.0 × 1.4` | 低重心、大きな外套膜、広い色面。押しにくそうな重量感 |
| `boss` | 第4Waveの最終ボス | `1.4 × 1.8` | 特徴的な突起の冠や装甲感。かわいさを残した威圧感 |

これらのIDは現在のゲーム接続のための仮IDであり、種族名や最終デザインではない。装飾はコライダーと分離し、胴体・接地部の基準を優先する。初回は静止モデルとし、移動方向への見た目の旋回・落下時の慌てる演出は後続作業にする。

### 4.4 ステージ01の床と設備

ステージは「メダルを積んで遊べる、縦長の人工的な遊戯装置」を最初の方向性とする。**海の中・海底・砂浜として制作しない。** 初回は第2.3節の意匠候補から2案を比較する。

外周は落下口として空け、床の縁と厚みで、どこから落ちるかを分かりやすくする。海洋オブジェクトを置く代わりに、面取り・ライン・質感差・間接的な装飾で世界観を作る。

| 制作物 | ステージGLB内のpath | 寸法・配置上の基準 | 希望する見た目 |
|---|---|---|---|
| 床 | `/root_game/floor` | `8 × 0.5 × 16`（X×Y×Z）。部品原点は厚み中央 | 上面が平らな台。縁と側面に面取り。メダルを見つけやすい天板 |
| 橋 | `/root_game/bridge_left`、`/root_game/bridge_right` | `5 × 0.5 × 1.6`。長手はローカルX。同じ形状を2か所へ配置 | 敵が渡る細い板橋。歩ける中央部分が見える。表面の溝は浅くする |
| 敵の出現足場 | `/root_game/spawn_left`、`/root_game/spawn_right` | `3.2 × 0.5 × 3.2`。同じ形状を2か所へ配置 | 橋とつながる小さな待機台。盤面外の入口だと分かる |
| ゴール | `/root_game/goal` | 外形の幅・奥行きは各1.0以内、高さ0.5前後を提案。部品原点は接地面 | 小さな受け口・ゲート・旗など、「ここに敵が来ると困る」と分かる設備 |
| カタパルト | `/root_game/catapult` | 幅・奥行き各1.2以内、高さ0.6を目安。接地原点 | 小さなおもちゃのメダル投射器。口が-Zを向く |
| レール（後続） | `/root_game/rail` | ステージ01の全長6.8。小さな反復部品から制作してよい | Pusher専用の移動範囲が分かる、床に沿った細い軌道 |

**Houdiniをステージエディタとして使う。** 床、橋、出現足場、ゴール、カタパルトを1つのGeometryネットワーク内で制作し、部品ごとにPackして配置する。敵・Pusher・初期メダルの生成はゲーム側で行う。

各Packed Primitiveに`path`を付けてMergeし、**形状と初期配置を含むステージ全体を1つの`stage_01.glb`へ出力する。** 部品の名前とTransformを残すため、全体を1つの巨大メッシュには結合しない。

現在の配置（床の上面がワールドY=0）。制作時の初回検証値とし、取り込み接続後の設備の初期配置はHoudini側のPacked PrimitiveのTransformを正本とする:

| 要素 | ワールド位置・範囲 |
|---|---|
| 床 | X=-4〜+4、Z=-8〜+8、Y=-0.5〜0 |
| 左橋の外端→内端 | `(-2.5, 0, -13)` → `(-2.5, 0, -8)` |
| 右橋の外端→内端 | `(2.5, 0, -13)` → `(2.5, 0, -8)` |
| 出現足場 | それぞれの橋の外端を中心に配置 |
| Pusherのレール | `(-3.4, 0, -1)` → `(3.4, 0, -1)` |
| カタパルトの接地原点 | `(0, 0, 5.8)` |
| メダル射出点 | `(0, 0.6, 5.8)`。初回はカタパルト基準のオフセット`(0, 0.6, 0)`をゲーム設定で使う。後続の`socket_muzzle`へ接続後は二重に加算しない |
| ゴールの接地点 | `(0, 0, 7.4)` |

ゴールの**判定半径は1.0**だが、前側の床端までの余裕は0.6しかない。制作する設備の足元を1.0×1.0以内に収める。

ゴール判定の高さ2.0はセンサー用の値であり、モデルの高さではない。

奈落は落下領域なので、初回に専用の底面モデルは必要ない。

### 4.5 SOP＋Packで作るステージの制作手順

**部品を作る → 原点を揃える → Pack → Transformで配置 → Primitiveの`path`を設定 → Merge → 階層付きGLB出力**を基本手順とする。カタパルトとゴールの配置は、それぞれのモデルを持つ名前付きノードから取得する。

初心者向けのノード操作順、PackのPivot、`Build Hierarchy from Attribute`、Houdiniへの読み直し、Bevy 0.20での取得方法は[ステージ制作・配置のワークフロー](houdini-stage-markers.md)に従う。初回は床・カタパルト・ゴールの3部品で往復確認する。射出口`socket_muzzle`は、空ノードの出力方法を検証した後に追加する。

## 5. Copernicusによる2D素材制作（必須）

**本作の2Dアート制作にもHoudini 22のCopernicusを使う。** メダルの図鑑サムネイルだけでなく、キャラクター選択画像、ステージ選択画像、メニューパネル、ボタン背景、飾り枠、バッジ、エフェクト用マスクなどを同じ制作環境から出力する。Bevy側で画像を手描き・再生成することを前提としない。Copernicusは**制作時**に使い、ゲーム実行時は書き出した画像を読み込む。

### 5.1 メダル89種の共通アートパイプライン

- SOPでメダルの共通円盤・必要な浅いレリーフ・UVを制作する。
- Copernicusで属性図案、模様、色分け、縁のハイライト、汚れ・発光マスクなどを**IDとパラメータで派生生成**する。`SDF Shape`、`Tile Pattern`、`Blend`、`Transform 2D`などを用途に応じて組み合わせる。
- 必要なメダルだけ高精細形状から`Bake Geometry Textures COP`で法線・AO等を低ポリゴン用UVへベイクする。**このノードは形状由来のマップが主対象**で、照明や材質表現を含むベイクはKarma Texture Baker等との役割分担を確認する。
- 同じ図案ソースから、①3Dメダル用テクスチャ、②図鑑アイコン、③選択画面サムネイルを出力する。3D用UV画像と2D用正方形画像は解像度・余白を別に調整してよい。
- 全89種の日本語名称とIDは既存カタログを正本とする。**ファイル名はIDに一致**させる。

### 5.2 UI・サムネイル制作

| 用途 | Houdini側の制作 | ゲーム側の役割 |
|---|---|---|
| メダル図鑑 | 共通フレーム＋各メダルを統一アングルで描画し、COPで余白・背景・陰影を調整 | 画像の表示、所持・未所持・レベルの状態表示 |
| キャラクター選択 | モデルの統一カメラからの画像＋COP仕上げ | 選択状態・名前・性能値の表示 |
| ステージ選択 | ステージ俯瞰レンダー＋COP合成 | ロック・クリア状態の表示 |
| メニュー背景・枠 | COPによる模様、面、枠、ボタン用背景画像 | `bevy_ui`でレイアウト・ヒット判定・フォーカス・入力処理 |
| バッジ・エフェクト | COPによる記号・グラデーション・マスク・ノイズ | 実行時の色変更、表示/非表示、アニメーション |

**重要：静的な装飾は画像で制作してよいが、言語切替対象の文字列、可変数値、ボタンのクリック判定は画像に焼き込まない。** 日本語・英語のラベルはBevyのUI/i18nで描画する。UI画像は通常のPNG等で独立納品し、GLBに内包しない。

- 図鑑アイコンはまず正方形・透過背景で試作し、64px・128px表示で識別できることを確認する。出力解像度は256pxまたは512pxから検証して決める（固定仕様ではない）。
- UIパネル・ボタン画像は拡大時の角の歪みを避けられる構成にする。必要なら中央と縁を分けて出力し、Bevy側の画像スライス対応を確認してから量産する。
- 通常色と必要な状態差分（選択中、無効、New等）は制作時に定義する。**文字入り完成画面を大量に書き出すのではなく、再利用できる画像部品**として納品する。
- 透過PNGなどで色縁が出ないよう、アルファ・色空間（sRGB/linear）・縮小時のにじみをBevy実機で確認する。

### 5.3 Copernicusの納品・再生成

Copernicusの編集可能なネットワーク（`.hiplc`等）と、**ゲームが直接読み込む画像**の両方を納品する。最終画像は`ROP Image COP`で書き出す。素材ID、画像用途、出力サイズ、アルファの有無、元のHIP/ネットワークを記録し、同じ設定で再生成できるようにする。89種類の図案を個別に手編集するよりも、共通テンプレート＋差し替えパラメータを優先する。

参考（SideFX公式）：[Houdini 22 Copernicus更新](https://www.sidefx.com/docs/houdini/news/22/copernicus.html)、[Copernicusノード](https://www.sidefx.com/docs/houdini/nodes/cop/)、[Bake Geometry Textures](https://www.sidefx.com/docs/houdini/nodes/cop/bakegeometrytextures.html)、[ROP Image COP](https://www.sidefx.com/docs/houdini/nodes/cop/rop_image.html)。

## 6. 動作とエフェクトの依頼範囲

最初の3Dモデル納品は静止モデルで進める。動作を追加する際は次の短いクリップを候補にする。

| 対象 | クリップ案 | 意図 |
|---|---|---|
| Pusher | `idle`、`move_forward`、`move_backward`、`push` | 呼吸、前進・後退、力を込めて押す |
| 敵 | `idle`、`walk`、`fall_react` | 待機、とことこ歩く、落ちるときに慌てる |
| カタパルト | `fire` | 小さな反動、機構が戻る |

クリップはその場で動くものとし、ルートの移動距離は付けない。物理移動と二重に動かさないため。

現在はアニメーションの選択・再生制御が未接続なので、リグや書き出し方式は静止モデルの取り込み確認後に合わせる。

破砕シミュレーション、ラグドール、メダルの落下の焼き込みは初回の制作範囲に含めない。

特殊メダルの効果処理はまだ未実装。火、湯気、風、爆発などのゲーム内VFX用素材は後続依頼とする。ただし、Copernicusで作る静止UI用の模様・マスク・試作エフェクトは第5節の範囲に含む。

## 7. Houdiniでの作り分けと納品形式

### 7.1 制作データ

編集可能なHoudiniプロジェクト（使用環境に応じた`.hiplc` / `.hiplclc`等）と、実行用GLBを納品する。

メダルは半径・厚さ・面取り・絵柄・材質を共通のSOP/COPネットワークから変えられる構成を優先する。3Dモデル、テクスチャ、2Dアイコンが同じID・図案を参照できるようにする。

HDA化は制作が楽になる場合だけでよい。ゲーム実行時にはHoudiniのネットワークを必要としない形にする。

### 7.2 実行用の書き出し

- 形式は **glTF 2.0の`.glb`**。画像を同梱した単体ファイルを基本とする。
- メダル・キャラクターは1ファイルに1アセット、1シーン。ステージは設備を含む全体で1ファイル、1シーンとし、名前付きの部品を`root_game`以下にまとめる。
- ポリゴンメッシュへ変換し、三角形化、法線、必要なUVを確認する。
- マテリアルはglTFで対応するPBRを出発点とする。Copernicusの画像をBase Color / Normal / Roughness / Metallic等の必要なマップへ変換し、**サポート外のHoudini固有シェーダーはそのままGLBに移植できると仮定しない**。書き出したGLBを別途読み直して検証する。
- カメラ・ライトの書き出しはOFF。初回はDracoなどの圧縮拡張を使わず、取り込みを確認してから検討する。

`.glb`への画像の同梱やカメラ・ライトの出力指定は[SideFX公式 glTF 2.0 ROP資料](https\://www\.sidefx.com/docs/houdini/nodes/out/gltf.html)を参照。

glTF 2.0書き出しはHoudini 22で導入された実装系統を用いる。旧ノードとの機能差があるため、個々のエクスポート対象（ノード階層・材質・アニメーション）の実機検証を優先する。

ステージはSOPの外側のPacked Primitiveにstringの`path`属性を付け、`Build Hierarchy from Attribute`をON、`Path Attribute`を`path`にする。描画メッシュと部品単位のTransformを同じGLBへ保持する。

### 7.3 置き場所と命名

```text

art/houdini/                       # 編集用ソース（新設する場合の提案）

  medals.hiplc

  pusher_nudibranch_concept.hiplc

  stage_01.hiplc

game/assets/models/

  medals/normal.glb

  medals/fire.glb                  # 以下、末尾のIDに対応

  pushers/<new_character_id>.glb

  # 旧PoC用ファイルは正式納品から除外

  enemies/grunt.glb

  enemies/brute.glb

  enemies/boss.glb

  stages/stage_01.glb              # 床・橋・出現足場・設備と初期配置を含む

```

ステージGLBは`game/assets/models/stages/stage_01.glb`へ置く。編集用ソースは`stage_01.hiplc`に含め、ステージ部品の個別GLBと配置専用GLBの納品は必須にしない。

メダルの実行用ファイルは既存の見た目定義に合わせ、当面`<id>.glb`を89種分出力する形を基準にする。同時に図鑑画像も`ui/medals/<id>.png`として出力する。

現在の見た目定義は、メダルIDごとにモデルのパスを指定する方式。共通のマスターから種類別ファイルを生成してよい。

Lv.1〜4では同じGLBと図案を使う。全種のMesh・材質の共有、テクスチャアトラス化や描画インスタンシングはゲーム側の実測後に検討する。

各納品には、ID、外形寸法、原点、三角形数、マテリアル数、テクスチャ/画像サイズ、アルファの有無、生成元ネットワークを簡単に記録する。

外部素材を使用した場合は、クレジットに記載できるよう出典とライセンスも添える。

### 7.4 確認用画像

- 最初の3D試作は、正面・上面・ゲームのカメラ角度から見た画像を添える。ステージは海洋装飾のない状態で2意匠案を比較する。
- メダルは同じ円盤を10枚積んだ状態、数十枚を並べた状態も確認する。
- Pusherは通常メダルと通常敵を隣に置き、大きさの比が分かる画像を添える。触角・外套膜・背面突起を上面から比較できるシルエットシートも添える。
- キャラクター選択・メダル図鑑・ステージ選択の画像もHoudini側で制作する。3DレンダリングとCopernicusを組み合わせ、モデルの変更時に再生成できるようにする。初回はノーマルメダルの図鑑画像を必ず添える。
- メニュー用のパネルまたはボタン背景の試作品を最低1点添え、ゲーム側の`bevy_ui`で縮小・拡大・文字重ねを確認する。

## 8. 軽さの制作目安

以下は**最初の制作を進めるための仮の目安**。実機性能を保証する上限ではなく、取り込み後にPC・iOSで計測して調整する。

| 対象 | 1個あたりの三角形数の目安 | 材質数の目安 |
|---|---:|---:|
| メダル | 150〜300、まず400以内 | 1 |
| 通常敵 | 400〜1,000 | 1 |
| Pusher・中ボス | 1,000〜3,000 | 1〜2 |
| 最終ボス | 2,000〜4,000 | 1〜2 |
| 床 | 1,000以内 | 1〜2 |
| 橋・足場・ゴール・カタパルト | 各500〜1,500 | 1〜2 |

メダルは数百〜数千枚が同時に出る。**物理コライダーは別**で、描画メッシュの輪郭に効く面取りへ面数を使い、小さな模様はCopernicusで作った画像で表す。

3D用テクスチャはまず512〜1,024px程度、図鑑アイコンは256〜512px程度を**検証開始値**とする。メダル89種類をすべて大きな個別テクスチャにするとメモリを消費するため、Windows/iOS実機で描画メモリとロード時間を測る。同じ画像・材質を使える部品は共有する。

不透明な表現を基本にし、透明な重ね合わせ、個別のライト、細かな多段階の部品階層は必要なものに絞る。

## 9. 取り込み時にプログラム側で対応すること

制作側で既存コードの都合をすべてモデルへ埋め込まなくてよい。次は接続時の実装作業として扱う。

| 項目 | 現在の状態と対応 |
|---|---|
| 見た目の指定 | メダル・キャラクターは`game/assets/visuals.visuals.ron`の`Appearance`キーからモデルを指定する。ステージGLB接続後は設備の見た目をGLB内のノードから使い、同じモデルを追加生成しない。旧PoC用Pusherのキーは新キャラIDへ移行するまで仮の接続として扱う |
| 2D UI画像 | Copernicus出力PNGを`bevy_ui`から参照する接続・画像状態管理はゲーム側で実装する。ゲーム文字列は既存i18nを使用 |
| 床・橋の形 | 現在の衝突形状はコード生成の単純形状。GLBノードの位置・向きを基準に配置する接続を追加する。見た目のメッシュからの自動コライダー生成は前提にしない |
| ステージGLB | 全体の読み込みとステージ構成への接続は未実装。最初は`floor`・`catapult`・`goal`を検証し、部品のEntityとステージ基準のTransformを取り込む。続いて橋・出現足場を接続する |
| ゴールの高さ | 現在は高さ2.0のセンサー中心、ワールドY=1へ見た目も付く。GLB接続時は見た目を`goal`の接地点へ置き、センサー中心だけ高さの半分を加算する |
| レール | 現在は移動経路のデータのみ。表示用部品はステージGLB内に追加できるが、経路データとの対応はゲーム側で接続する |
| キャラクターの向き | Pusherは最初のレール方向に合わせた向きで固定。敵も進行方向への見た目の旋回は未接続 |
| 動作・射出機構 | カタパルトの初期配置はGLBから読み、ゲーム中の旋回・アニメーションは後から接続する。射出口`socket_muzzle`はSOPからの空ノード出力を検証後に追加し、既存オフセット・仰角と二重に加算しない |
| 差し替え | モデルの初回ロードと実際の差し替えをゲーム上で確認する。ファイルの再読み込みだけで既存Entityが張り替わるとは前提にしない |

個別生成するメダル・キャラクターのキーと納品モデルの対応例:

```ron

"medal/normal": Model(scene: "models/medals/normal.glb#Scene0"),

"pusher/<new_character_id>": Model(scene: "models/pushers/<new_character_id>.glb#Scene0"),

"enemy/grunt": Model(scene: "models/enemies/grunt.glb#Scene0"),

```

ステージ全体は`models/stages/stage_01.glb#Scene0`として1回だけ展開する。接続実装時に、現行の設備用`Appearance`による見た目生成を停止し、展開済みの部品ノードを利用する。

最初の納品を取り込んだら、床と足元の接地、メダルの上下面、橋の向き、カメラからの視認性、描画負荷をゲーム上で確認してから残りを量産する。
