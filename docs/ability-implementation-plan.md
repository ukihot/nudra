# 能力システム実装課題（基本設計 v0.2）

- 作成日：2026-11-20
- 対象：[基本設計書 v0.2](basic-design.md) の3.14〜3.18、4.3、5.3〜5.6、6章、8.5、9〜10章
- 状態：設計改訂と実装課題の整理まで。以下の実装・テスト・実機計測は今回実施していない。
- 追加レビュー：排他的Systemでの確定、`OtherFell` の候補生成上限、支持接触による着地、進化時の差分更新を追補した。

基盤は維持する。まず共通処理の不整合と安全策を直し、6種の能力で成立性を確認する。
既存の89種の識別・表示名・錬成データは維持し、残り83種の能力定義の量産は検証後に進める。

## 現行コードとの照合

以下はソースと既存テストの記述を読んだ結果であり、今回のテスト実行結果ではない。
開始時点で能力関連のステージ済み変更が存在していたため、その作業内容も含めて照合した。

| 能力消滅・復活で通常報酬を得られる | `expire` は `vanish` を `MedalsFell` へ加算。`medal_falls` は復活判定前に価値を合計 | 実装の修正が必要。退場原因・報酬資格・最後の落下を区別する |

| 個体の `uses` だけでは増殖を防げない | [AbilityBook](../crates/domain/src/spec/abilities.rs) は一部Spawnの回数／封印を検証。世代・実行時予算はない | P0で世代・予約枠・上限時の処理を実装。Splitも同じ経路へ接続 |
| 発動と物理適用が別の時点 | [firing.rs](../crates/domain/src/firing.rs) は回数・ゲージ等を先に変更。`execute_orders` は別にまとめて適用し、生成中の指示は次tickへ残す | 計画と確定を分離。満タン時の未確定指示を全経路で止める |
| 能力ごとの遅延Command反映が具体化されていない | 現行の `execute_orders` は `Commands` に生成・退場を積み、ループの次の能力へ進む | P0-4で排他的SystemからWorldを直接更新する方式を採用。ループ内での一括flushに頼らない |
| `OtherFell` が予算判定前に大量化する | `medal_falls` は落下件数ぶん全メダルを巡回する | P1-4で購読索引・遅延列挙・検査4,096件/tickの上限を導入。全組のVecやMessageを作らない |
| 壁への衝突が着地になり得る | `collisions` は非センサーへの接触を `Touching` に入れ、挙動観測で接地とする | P1-5で接触法線・点・分離速度による支持判定へ置換 |
| 進化時に能力状態をどう更新するか不足 | `set_level` は回数を保持するが、`accept_evolution` は `AbilityTimers::new(now)` で全期限を再作成 | P1-6で既存能力の期限・消費状態を保持し、覚醒の追加分だけ初期化 |
| releaseの継続に原子性の保証がない | [main.rs](../game/src/main.rs) はreleaseでログ出力ハンドラを設定 | 適用前検証と安全な中断を追加し、未処理の失敗から継続しない |
| 6種同時の実証がない | [gameplay.rs](../game/tests/gameplay.rs) の能力テストは山・幻・水・炎・星など部分的。[RON](../game/assets/data/game.specs.ron) の雷は接触発動で、爆弾・水分身・ゾンビの能力定義はない | 部分テストを活用し、周期の雷を含む6種と同時動作のテストを追加する |

AvianのMessage生成条件は、ローカルの `avian3d-0.8.0/src/collision/collision_events.rs` で確認した。
ペアの片方に `CollisionEventsEnabled` があればMessageが生成される。受信後の両側の能力判定が必要である。

## 優先順位と完了条件

### P0-1：退場と報酬の共通化

- 対象：`domain::unit`・`session`、application `resolve`・`abilities`、game `physics`・`abilities`・`world`・データ読込。
- 退場原因、個体の報酬資格、復活消費数を定義する。`vanish` / `Remove` / `Consumed` / `Transform` は通常報酬を出さない。
- 初期配置・射出・生成・分割で資格を設定し、変化や価値の印で資格を増やさない。
- 復活は同じ個体・期限・回数・世代を保持し、最後の落下だけ通常報酬を生む。
- 敵に禁止された退場効果を読込時に拒否し、撃破はDomainの生存集合と同期する。
- 完了条件：退場原因別、センサー＋安全高度、復活の全回数、有価／無価生成、ボス落下をテストし、二重報酬0。

### P0-4：計画・適用前検証・確定の分離

- 対象：`domain::firing`・`GameSession::fire_ability`、application `abilities`、game `PendingOrders`・`execute_orders`・スケジュール。
- 計画を作るだけでは回数・ゲージ・乱数・履歴を変更しない。
- 対象、状態効果と反応、生成、再生分、予算をまとめて検証し、1能力を全体受理／全体棄却する。
- 排他的Systemの内部で1能力ずつ計画・検証・直接World更新・通知を完了する。ResolveとAbilitiesから同じ確定関数を使う。
- ループ内では `Commands` や `World::flush()` を使わず、別SystemやObserverからゲーム状態を変更させない。
  生成・復活の `Position` / `Rotation`・速度を明示し、次の能力の検索が物理初期化を待たず正しい状態を読むようにする。
- 1能力の適用途中に通常の検証エラーを残さない。排他実行による直列性と、ロールバックによる原子性を混同しない。
- 満タンなら現在の受理済み能力だけ完了し、別Entityを含む未受理計画を破棄する。必須の物理結果は処理し切る。
- 完了条件：「印＋生成」の生成枠不足、同tickの爆発3個、先行効果で対象が消えた場合、再生の不成立で不整合がない。
  1個目が生成した個体を2個目が正しい位置で検索でき、1個目が退場させた個体へ2個目が適用されないことを実Bevyで検証する。
- 依存：P0-1〜3。巨大なtick全体トランザクションを作らず、1能力の境界に限定する。

### P0-5：失敗時の中断とrelease設定

- 対象：game `main`・`session`・能力／進化の適用・セッション後片付け。

- セッションを勝敗未確定のまま片付けて選択へ戻す。整合性を保証できなければ異常終了する。
- 完了条件：途中失敗を注入し、追加生成・時計進行・誤ったクリア保存がなく、キュー・盤面・Resourceが片付く。
- 依存：P0-4。検証用Appだけでなく、releaseのFallback設定も検査対象とする。

### P1-4：`OtherFell` の候補生成を制限する

- 対象：gameの購読索引・退場文脈・能力列挙、applicationの検査枠。基本設計3.18・6.2。
- 購読能力だけを整列して保持し、落下ごとに全メダルを検索しない。生成・退場・変化・進化時に索引を更新する。
- 落下×購読能力を遅延列挙し、条件判定より先に検査枠を消費する。4,096件で残りの列挙を止める。
  封印・使用回数切れ等で能力が受理されなくても、候補検査の上限を守る。
- 完了条件：500件落下×3,000購読能力で、検査数が最大4,096、発動数が最大256となる。
  全購読者が封印中で発動0の場合も同じ検査上限を守り、150万件の候補配列・Message・理由ログを作らない。
  必須の退場・報酬・Goal判定は500件すべて処理し、候補打切り後の持越しがないことを確認する。
- 依存：P0-2〜P0-4。候補の実検査数・最大同時保持数を診断し、性能テストでも検証する。

### P1-5：支持接触による着地判定

- 対象：gameの物理観測・`Touching`・`MotionSample` の生成。基本設計5.4。
- `CollisionStart` と接地判定を分け、継続中のtouching接触から法線・接触点・相対分離速度を調べる。
- 仮の支持条件は上向き法線の内積0.5以上、接触点が中心より下側、接触距離2mm以内、分離速度0.2m/s以下。
  センサー、遠い投機的接触、天井・横壁は支持にしない。復活・テレポート・形状変更後は古い観測を使わない。
- 完了条件：床・許容傾斜・メダル上への着地では `Landed` が1回出る。
  壁だけ・天井だけ・センサーだけ・投機的な近接・跳ね上がり中は着地せず、壁の `Collide` は独立に発動できる。
  接触開始を逃した継続支持、スリープ中の支持相手、復活・`lift` 後の再着地も実Avianで検証する。

## 実装時の検証手順

リポジトリの [CLAUDE.md](../CLAUDE.md) に従い、変更対象の振る舞いをRED→GREEN→REFACTORで確認する。
gameも変更するため、仕上げは以下の順で実行する。

```sh
cargo +nightly fmt --all
cargo clippy -p domain -p application -p game --all-targets
cargo nextest run -p domain -p application -p game
```

これに6種の混在シーンとPC・iOS実機の計測を加える。テスト数だけで通過を判断しない。
各課題が完了したら、変更したコミット・実行条件・結果・残る制約をこの文書に記録し、
基本設計の【実装差分】と12章の仮決定も更新する。
